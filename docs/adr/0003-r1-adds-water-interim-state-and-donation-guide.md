# ADR-0003: R1 に「水道の用途別可否」と「寄付窓口の判別」を入れ、型は増やさない

- 日付: 2026-08-02
- 状態: **提案中（原文未照合）** — 後述「この ADR を承認済みへ移す条件」を満たすまで確定しない
- 関連: `docs/needs/2026-08-02-needs-triage.md`、`docs/design/concept.md`、`docs/adr/0002-area-map-uses-municipality-tiles-not-pins.md`、`lib/disaster-data.ts`（`ActionCard` 型の `verifyPoints` / `facts` / `irreversibleOrder` と `patrolled()`）、`tests/data-contract.test.mjs`（`ALLOWED_SOURCE_HOSTS`）

## 文脈

2026-08-01〜08-02 に運営者が記録したニーズ観測16件と、確定後に受領した追加観測 #17（停電情報）をトリアージし、現行の約束（読み取り専用・稼働状況を判定しない・実行時の外部通信ゼロ・巡回1日1回で維持できる粒度）に照らして3分類した（`docs/needs/2026-08-02-needs-triage.md`）。R1 に入れる候補は **#1 水道の中間状態** と **#10 寄付窓口の判別** の2件で、2026-08-02 に運営者が選定済み。

観測で最も繰り返し現れた構造は「**二値では足りない**」だった。#1 #2 #3 #4 #5 #15 #16 の7件が独立に同じ形をしている——「復旧した／営業中／開設中」では判断できず、**用途別の可否**と**最終確認時刻**が要る。#1 について運営者は「全ライフラインに共通するデータモデルとして実装すべき」と記している。

この ADR が決めるのは、その要望を **新しい型で受けるか、既に持っている機構で受けるか**である。判断の材料として実装を読んだ結果は次のとおり（2026-08-02 実測）。

| 事実 | 根拠 |
|---|---|
| 用途別の可否を出す機構は既にある | `ActionCard` 型の `verifyPoints`（`{ label, options, why }`。「options には出典ページに実際に書かれている区分だけを入れる。区分を推測で作らない」と型のコメントが規約化している） |
| その先例も既にある | 既存の水カードが label「水の用途」/ options「飲料用・生活用水」/ why（水質検査10項目を満たしたものが飲料用、生活用水は飲むために提供されていない、災害後の再検査で飲めなくなり得る）を持つ |
| 時刻はカード単位で3つ持っている | 同型の `publishedAt`（出典の最終更新）/ `fetchedAt`（取得）/ `checkedAt`（確認） |
| 巡回はカード単位で時刻を書く | `patrolled()` が `PATROL_AT` を `fetchedAt` と `checkedAt` へ一括で入れる。`docs/OPERATIONS.md` の再確認巡回はこの2つだけを書き換える運用 |
| 「行けば受け取れる時間」は別軸で分離済み | 同型の `availableWindows`（型コメント: `expiresAt` は「この情報をいつまで信じてよいか」、こちらは「行けば受け取れる時間はいつか」） |
| 不可逆な手続きの順序を出す機構もある | 同型の `irreversibleOrder`（実例「支払いや契約の前に、公式窓口へ相談する」「片付けや修理の前に、家屋の被害状況を写真に撮る」） |
| 出典ドメインは機械で強制されている | `tests/data-contract.test.mjs` の `ALLOWED_SOURCE_HOSTS` が7ドメインを正規表現で固定（`pref.kumamoto.jp` / `city.kumamoto.jp` / `tca.or.jp` / `qsr.mlit.go.jp` / `enecho-ss.meti.go.jp` / `town.hikawa.kumamoto.jp` / `kumamoto-waterworks.jp`） |

## 決定

### 1. #1「水道の中間状態」は、既存機構でカード単位に表現する

八代市の試験通水のような「水は出るが飲んではいけない」中間状態を、次の3つで表す。新しいフィールドは足さない。

- **用途別の可否** → `verifyPoints`（既存の水カードと同じ label「水の用途」の形）
- **公式発表に書かれている事実** → `facts`（出典に書かれている記載だけを転記する）
- **混同すると健康被害につながる注意** → `caution`
- **最終確認時刻** → 既存の `publishedAt` / `checkedAt`（巡回が `patrolled()` で更新する）

運営者の「全ライフラインに共通するデータモデル」は、**新しい型ではなく既存機構の適用パターン**として満たす。同じ形が #15（薬局: 「開局中＝調剤できる、ではない」）と #3（避難所: 「開設中＝猛暑下でも安全、ではない」）へそのまま横展開できる（トリアージ文書のクラスタ1）。

### 2. ライフラインごとに「転記型」と「リンク型」を使い分ける

同じ「二値では足りない」でも、公式側が持っているものによって扱いを変える。

- **転記型（水道）**: 公式発表が静的な告知として出る領域。`facts` へ書かれている記載を写す。写した時点が `publishedAt`、確認した時点が `checkedAt` で、両方を画面に出す
- **リンク型（電力）**: 公式に生きたツールがある領域（#17 の九州電力送配電の停電情報ページ）。**導線と「何を確認すべきか」だけを出し、停電件数・復旧見込みの数値は転記しない**。分単位で変わる値を巡回1日1回で写すのは、唯一の品質基準（鮮度と失効を正直に出す）と正面から衝突する。公式に生きたツールがある領域で、アプリの役割は複製ではなく導線である

### 3. #10「寄付窓口の判別」は、新カード1枚（コンテンツ追加）として入れる

義援金／寄附金／支援金の3種の違いの解説と、公式窓口へのリンクを出す。機能開発はしない。送金は不可逆なので、既存 `irreversibleOrder` の思想（支払い・契約の前に相談する）と同型に置く。

**これは R1 非実装リストの「寄付決済」とは別物である**。アプリが行うのは公式窓口への案内だけで、募金の受付・寄付金の収受は行わない。この線は次の3か所が既に宣言しており、本カードはそれを1つも崩さない。

- `docs/DESIGN.md`「利用者投稿・支援要請・寄付・決済：提供していません」
- `docs/design/screens.md`（画面に出す同じ文言）
- `docs/kumamon/notification-draft.md`「募金の受付・寄付金の収受・物品販売は一切行いません」（くまモンイラスト使用の届出で対外的に宣言している）

### 4. R1 は上記2件で固定する

トリアージで `(a)条件` とした #3 #4 #5 #7 #13 #15 は確度[中]のまま据え置き、この ADR で昇格させない。

## 却下した案

### `ActionCard` を項目単位（用途ごとの可否＋用途ごとの最終確認時刻）へ拡張する

要望の字面に最も近いのはこの案で、実際に検討した。却下した理由は**情報が増えないから**である。

巡回は `patrolled()` が `PATROL_AT` を全カードへ一括で入れる運用なので、項目単位の時刻を型に足しても、入る値はカード単位の `checkedAt` と同じになる。「飲料用は 11:25 確認、生活用水は 11:25 確認」と並ぶだけで、利用者が受け取る情報は1文字も増えない。

一方でコストは残る。`lib/disaster-data.ts` の型変更、`tests/data-contract.test.mjs` ほかの機械固定の更新、`scripts/generate-mobile-data.mjs` 経由でネイティブ側へ複製されるデータ形式の同期が要る。

項目単位の時刻が意味を持つのは、**項目ごとに違う時刻が実際に入るとき**——つまり巡回が用途別に別々のページを別々の時刻で確認する運用になったときである。そのときは本 ADR を更新して再検討する。現在の巡回（1日1回・カード単位）ではその条件を満たさない。

### クラスタ3「認証済み関係者の内部運用」（#2 #11 #12 #14、#6 の運搬・#13 の写真管理・#14 の割当て）

福祉施設の受入能力、要配慮者のホテル避難調整、炊き出しの食数・配布先調整、ボランティアの受付・割当て。これらは運営者自身が観測時点で「価値があるのは認証済み関係者の内部運用」「正式連携前は公式情報の横断表示までに限定すべき」と結論している。

現行の約束（利用者投稿・個人情報・認証を持たない／事業者や自治体からの実行時更新経路を持たない）の外にあり、**このリポジトリでは作らない**。作るなら別プロダクトとして要件からやり直す。

### クラスタ4「既存あり・アプリでは解決にならない」（#8 #9 #16）

- #8 公共交通の停止 — 既存の集約サイトを八代市が公式に案内済み
- #9 支援物資の配送不能 — 「アプリ単独では輸送能力を生み出せない」（運営者記載）。荷受停止の公式発表は既存カードの `facts` で扱える
- #16 充電・操作支援 — 「スマホを使えない人をアプリだけで支援する設計は成立しない」（運営者記載）。充電スポットの公式情報は #5 の範囲へ統合

### #17 停電情報を R1 に加える

分類は `(a)条件` [高]（公式ページへの導線と確認観点まで）だが、R1 の選定は変えない。本 ADR では「リンク型」の考え方を示す文脈として使うにとどめる。

## 根拠

この決定の核心は、**7件で独立に現れた「二値では足りない」が、新しい思想ではなく現行の約束の適用範囲の話だった**という読み替えにある。

「用途別の可否を、行く前に確認できる形で出す」は、既存の水カードが井戸水について既に実行している。#1 が求めているのは新機構ではなく、同じ扱いを試験通水という別の中間状態へ広げることである。型を増やさない判断は、機能を削ったのではなく、**既に持っているものを数えた結果**である。

#10 を入れる理由は別で、送金が**不可逆**だからである。行き先を間違えた送金は取り消せない。義援金（被災者へ配分される）・寄附金（自治体の財源になる）・支援金（団体の活動費になる）は、名前が似ているのに届き先が違う。既存 `irreversibleOrder` が「支払いや契約の前に、公式窓口へ相談する」を出しているのと同じ理由で、送金の前に判別を挟む価値がある。窓口情報は日単位で変わらないので、鮮度リスクも巡回コスト増分も全カードの中で最小になる。

## 影響

### 実装時に出典ドメインの追加が要る（2026-08-02 実測。トリアージ時点の想定より広い）

トリアージ文書は「#17 をカード化する場合のみ `ALLOWED_SOURCE_HOSTS` の追加が要る」としていたが、実装を読み直した結果、**#1 も同じ制約に当たる**ことが分かった。

- 現行19カードの出典ホストは7種類で、**八代市の公式サイトは1件も無い**（八代市を `areas` に含むカードは1件あるが、出典は国土交通省九州地方整備局）
- したがって #1 を**八代市の試験通水ページを出典として**カード化するなら、八代市ドメインの `ALLOWED_SOURCE_HOSTS` 追加とテスト更新が要る
- #10 も同様に、出典が熊本県（`pref.kumamoto.jp`、許可済み）の義援金ページに収まるなら追加不要だが、日本赤十字社・共同募金会・支援団体のページを直接指すならドメイン追加が要る
- #17（`kyuden.co.jp`）は R1 外だが同じ制約

いずれも小さい変更だが、**機械で強制している境界を緩める変更**なので、カードを1枚足すより明示的に扱う。実装タスクの着手時に、追加するドメインを1件ずつ決めること。

### そのほか

- 実装は本 ADR の承認後・別タスク。着手時に一次情報を取り直す（#1＝八代市の試験通水ページ、#10＝公式窓口ページ）。観測は 8/1〜8/2 時点で、状況は日単位で変わる
- 型変更は行わないため、`lib/disaster-data.ts` の型・`scripts/generate-mobile-data.mjs` 経由のネイティブ同期・既存テストへの影響はいずれも無い。増えるのはカードのデータと巡回対象のページだけ
- カードが増えた分だけ巡回コストが増える。#10 の窓口情報は日単位で変わらないため増分は小さいが、#1 は断水状況の更新に追随する必要がある
- `docs/design/concept.md` は「R1で実装しない機能は `README.md`「これは何か」に要約されています（…寄付決済…）」と書いているが、README のその節に寄付・決済の記載は無い（2026-08-02 実測）。指し先のズレであり、本 ADR は README を参照先に使わない。修正は別タスク
