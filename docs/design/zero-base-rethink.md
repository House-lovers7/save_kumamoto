# 設計仮説 — 同じ問題をゼロベースで解き直すなら

作成: 2026-08-03 / 位置づけ: **設計仮説メモ**（R1 のスコープ外。実装計画ではない）/ 出典: 本リポジトリの実装・設計文書から抽出した実測知見 + 未検証の仮説。確度タグ（[高]=実測・文書で確認済み / [中]=複数の根拠から推定 / [低]=仮説・要検証）を各節に付す。

> 問い: 「災害下の被災者支援」という同じ問題を、IT に限定せずゼロベースで解き直すなら、何が最適解か。

## 1. 問題の再定義 [高]

本リポジトリの開発で確定した最重要の発見は2つある。

1. **災害時の問題は「情報が無い」ではなく「どれが今も有効か分からない」**（`docs/DESIGN.md`「解こうとしている問題」）
2. **現在の稼働状況は、現場からの更新経路が無ければ原理的に出せない**（同「このアプリが引き受ける範囲」）

したがってこれは情報配信の問題ではなく、**信頼のサプライチェーン**の問題である。

```text
現場の事実 → 観測 → 運搬 → 検証 → 配布 → 意思決定
（給水車がいる）（誰かが見る）（断絶下で運ぶ）（いつ時点か）（届く）（行くか決める）
```

本アプリは下流3段（検証・配布・意思決定)を誠実に実装し、その過程で**上流2段（観測・運搬）が社会側に存在しない**ことを言語化した。ゼロベースで解くなら、作るべきは上流である。

> **2026-08-03 の照合による訂正**: 「存在しない」は言い過ぎだった。標識の標準（JIS Z 9098）も、「避難所の開設状況を周知する」という業務の定義（内閣府 避難所運営ガイドライン）も存在する。存在しないのは**運用状態を表す語彙と様式**、および**現場自身がそれを宣言する主体設計**である。詳細は [signage-protocol.md](./signage-protocol.md)。

## 2. 盤面の勝ち筋4つ [中]

1. **被災者の最少資源は「往復」**（体力・燃料・時間）。最悪の失敗は「行ったら使えなかった」。システムの目的関数は情報量ではなく**無駄往復の最小化**。
2. **最も正確な情報の保持者は現場にいる。** 給水所の状態を一番知っているのは給水所自身。真実の座を「自治体の Web ページ」から「現場」へ移す。Web ページは現場の遅延コピーにすぎない。
3. **無駄足をした人は、次の人の無駄足を防ぐ情報を持って帰る。** 観測は毎時間発生していて、ただ捨てられている。問題は観測の生成ではなく回収と検証。
4. **平時に使われない仕組みは本番で使われない。** 災害専用アプリ・災害専用機器は訓練でしか触られず死ぬ。日常運用される仕組みに災害モードを内蔵するのが唯一の生存経路。

## 3. 解のアーキテクチャ（IT 非限定・6層） [低]

| 層 | 中身 | IT度 |
|---|---|---|
| **L0 現場状態の標準化** | 給水所・避難所・店舗が状態を宣言する**物理標識の標準**（開設中/時間外/終了/移動先○○へ）。紙と A 型看板が主役。国・自治体の様式標準が本体。**→ 一次情報で照合済み・[signage-protocol.md](./signage-protocol.md)。「標識の標準が無い」は不正確で、避難誘導は JIS Z 9098 として存在する。無いのは運用状態の語彙と、宣言する主体の設計** | 非IT（制度） |
| **L1 現場アテステーション** | 標識に印刷 QR・NFC・日替わりコードを併設し、現場の状態宣言を**機械検証可能**にする。信頼の根拠を「誰が言ったか」でなく「現場で発行されたか」に置く | 軽IT |
| **L2 人流ストア&フォワード** | 帰還者・広報車・スマホ（BLE/Wi-Fi Direct）が L1 の署名済み観測を運ぶ。現場署名だけ検証すればよいので**運び手を信頼する必要がない**＝本アプリの読み取り専用・利用者投稿なし原則と両立する | 中IT |
| **L3 縮退の梯子** | Web → 静的 CDN（現行）→ SMS/セルブロードキャスト → ラジオ原稿 → 避難所の紙 → 現場標識。**同一データモデルから全媒体へレンダリング**し、各層が下の層を生成する | 混合 |
| **L4 意思決定支援** | 「行く前に何を確認できれば無駄足にならないか」を全カードで明示（現行 `verifyPoints` / `irreversibleOrder` / `facts` の一般化） | 現行資産 |
| **L5 制度と訓練** | 標準の所有者（県・国）、平時利用（通常の営業時間表示と同一の標識/QR）、防災訓練への組込み | 非IT |

## 4. 現行実装の位置づけ [高]

`ActionCard` 型（`expiresAt` / `facts`+`citedAs` / `sourceStatus` / `verifyPoints`。`lib/disaster-data.ts`）は、期限・出典・未確認の明示を構造として持つため、Web 専用の型ではなく**媒体非依存の中間表現**として機能しうる。そのまま A4 掲示物にもラジオ読み上げ原稿にも降ろせる。つまり本リポジトリは L3 の一段 + L4 を実装済みで、この構想の中で最も難しい「誠実性の規律」（推測で埋めない・失効を隠さない・それをテストで機械強制する）を既に検証している。

### 4-1. 紙レンダラーによる実証の結果（2026-08-03） [高]

上の主張を実物で確かめた。`lib/poster.ts`（`posterModel` = 何を載せるかの判断／`renderPosterHtml` = A4 の紙に組む）と `scripts/render-poster.mjs`、`tests/poster-render.test.mjs` を実装した。**結論は「条件付きで成立」**。

**成立した点**

- 全19枚のカードが、期限内・期限切れのどちらでも例外なく紙へ降りた（`tests/poster-render.test.mjs`「全カードが紙へ降りる」）
- 期限・出典・未確認の判定を紙のために書き直す必要がなかった。`isExpired` / `visibleFacts` を正典からそのまま呼べている。判定が1か所にあるので、Web は失効を隠さないのに紙は隠す、という食い違いが起きない
- 「何を載せるか」（`PosterModel`）と「どう見せるか」（HTML）を分離できた。次の媒体を足すときに判断ごと書き直す必要は無さそう、というところまでは確認できた（ラジオ原稿は未実装なので断定はしない）

**成立しなかった点 — データは降りるが、文言が媒体に依存している**

これがこの実証の本当の収穫である。型は媒体非依存でも、**中身の文章が画面を前提に書かれている**。

| 項目 | 何が起きたか | 対処 |
|---|---|---|
| `action` | 「上下水道局の緊急情報を**開く**」。タップできる媒体でしか意味を持たない | 紙へ降ろさない（`PosterModel` から除外） |
| `steps` | `water-station` の手順1が「上下水道局の緊急情報で今日の応急給水所のお知らせを**開く**」。端末を持たない読み手に実行できない指示が紙に載る | **レンダラーでは直せない**。型は媒体依存の文言を禁じていない |
| `caution` | 「**このアプリは**給水を保証しません」。紙に刷ると一人称が指す先が消える | 同上 |
| `dated` の粒度 | 当日限りかどうかのフラグが `facts` にしか無い。`summary` と `verifyPoints` にも「南区5か所・西区1か所」のような当日限りの内容が書かれている | 失効後は `summary` `steps` `verifyPoints` `irreversibleOrder` をまとめて落とす。結果、期限切れの紙に残るのは問い合わせ先だけになる |
| 受付時間帯の判定 | 画面は「いまは受付時間外です」と断定できるが、紙は刷った時刻でしか判定できない。4時間後に読んだ人へ嘘になる | `serviceWindowNotice` は紙で使わず、枠（9:00〜11:00 / 15:00〜17:00）のまま刷って判定を読む人の時計に委ねる |

**含意**: 「同一データモデルから全媒体へ」（§3 L3）は、データ構造の問題としては解けているが、**文言の媒体依存という別の層が残っている**。ラジオ原稿へ進む前に、(a) 媒体依存の文言を型で分離する（`action` のように媒体別フィールドを明示する）か、(b) 運用規約で「`steps` に媒体名を書かない」と縛るかの判断が要る。この判断は R1 のカード文言に影響するため、運営者の決定事項になる。

**決定（2026-08-03 運営者）: (b) 規約+機械検査を採用し、同日実装した。** 型は媒体別フィールドを持たず、文言そのものを媒体非依存に保つ。理由は、このリポジトリの誠実性規律がすべて「規約を機械検査で固定する」型で通っていること、媒体別フィールドは媒体が増えるたび（次はラジオ原稿）型と19カード分の記入が増えること。実装は次の2点。

- 正典の文言9件を媒体非依存へ書き直した（`steps` 1件「〜を開く」→「〜を確認する」、`caution` 7件「このアプリは」→「この案内は」、`summary` 1件「古い画面を開いている場合は」→「古い情報の場合があるため」）。§4-1 の表で挙げた `steps`/`caution` に加え、grep で `summary` にも同じ層の違反が1件見つかったため、検査対象は紙に載る文言フィールド全体（`summary`/`steps`/`facts`/`verifyPoints`/`irreversibleOrder`/`caution`/`unverified`）とした
- `tests/data-contract.test.mjs`「紙に載る文言に画面前提の語彙を書かない」で禁止語彙（を開く・タップ・クリック・このアプリ・本アプリ）を機械強制した。検査自体の負例（違反例を検出できること）もテストで固定してある。`action` は画面のボタンラベルで `PosterModel` から除外済みのため対象外

**A4 1枚に収まることを確認済み[高]**（2026-08-03 運営者目視）: `work/poster-water-station.html` をブラウザの印刷プレビュー（A4縦・既定余白）で開き、ページ数表示が **1/1** であることを運営者が確認した。あわせて紙面の全文テキストも運営者が目視し、内容の欠落がないこと・文言修正（手順1「〜を確認する」・注意書き「この案内は」）が紙面へ反映されていることを確認済み。ブラウザ自動操作の権限は付与せず、運営者の目視で閉じた。

## 5. この盤面で証明できること [中]

実装力・アーキテクト力の証明は機能の多さではなく次の4点にある。

1. 誠実性制約下の設計（unknown を unknown と言い、機械で強制する）
2. 縮退設計（インフラが死ぬ順に応じた梯子）
3. 信頼アーキテクチャ（真実の座をどこに置くかの設計）
4. 制度とソフトウェアの結合（標準・訓練・平時利用まで含めた解）

これは高信頼領域（医療・金融・インフラ）へ一般化できる型である。

## 7. 発信者アイデンティティ層 — 運営者アイデア（2026-08-03）

運営者提案: 発信者をマイナンバーカードに紐付け、審査を通った人だけが発信できる SNS 的ツールを作る。

**位置づけ**: §3 の L1/L2 の**人アンカー版**である。本メモの L1 は「場所」に信頼を置く（現場発行の署名）。この案は「人」に信頼を置く（本人確認済み + 審査済みの発信者）。両者は排他ではなく直交し、組み合わせると観測の出所が**「誰が・どこで・いつ」の3点**で検証可能になる。

強み:

- 匿名クラウドの偽情報問題を入口で遮断し、公式（自治体）と群衆の間に「審査済み観測者」という中間信頼層を作る。アナログの先例は民生委員・防災士・自主防災組織で、その台帳と身分確認をデジタル化することに相当する
- 発信に説明責任が生まれ、悪意・誤りの発信へ事後対処（資格停止）できる

### 7-1. 制度の一次情報照合（2026-08-03 実施） [高]

前版はこの節を記憶ベースで書いていた。当日の公式一次情報で照合した結果、**方向は正しく、細部は2点誤っていた**。以下は照合済みの事実である（出典は本節末尾）。

**個人番号（12桁）そのもの**

- 番号法は個人番号を利用できる範囲を「社会保障、税、**災害対策**その他の行政分野に関する特定の事務に限定」している（番号法第9条）。本人の同意があっても目的外利用はできない
- さらに「何人も、特定個人情報の提供を受けることが認められている場合を除き、他人に対し、個人番号の提供を**求めてはならない**」（第15条）。収集・保管にも同様の制限がある（第20条）
- つまり本案で12桁の番号を発信者IDに使うことは、**取得を求める行為の時点で禁止**にあたる。「使わないほうがよい」ではなく「求めてはならない」。前版の「制限されている」は弱すぎた
- 「災害対策」が法定の利用分野に入っているのは行政機関等の特定事務についてであって、民間の観測者ツールがそこへ入れるという意味ではない

**JPKI（公的個人認証）電子証明書側**

- 民間事業者が署名検証者になるには、**主務大臣（内閣総理大臣及び総務大臣）**の認定を受け、J-LIS へ公的個人認証法第17条第1項の届出をする。前版は「総務大臣」と書いていたが誤りで、**内閣総理大臣及び総務大臣の両方**が主務大臣
- 認定が必要になる実体上の理由は、電子証明書の**失効情報**の入手（同法第17条第1項第6号）。失効情報の提供範囲を認定事業者に限定することで不適切な利用を抑止する設計になっている
- 認定基準は8個の評価項目（規程類の整備、不正アクセスの防止、権限のない者による操作の防止、動作を記録する機能ほか）で、審査は**書類審査及び現地調査**。根拠は公的個人認証法施行規則（平成15年総務省令第120号）と技術的基準（総務省告示第706号）
- **重要な発見**: いわゆる**プラットフォーム事業者（サービスプロバイダ事業者）へ委託すれば、委託する側は主務大臣の認定も機構への届出も不要**になる特例がある（施行規則第29条のみなし規定）。前版は「民間サービスの利用には認定が必要」と書いたが、**自前で認定を取る以外の道がある**。少数の観測者を抱える災害用ツールが、単独で認定・現地調査を通す必要は必ずしもない
- ただしサービスプロバイダ事業者には禁止事項がある——①本人から提出された電子証明書を保持してはならない ②電子証明書の発行番号を取得・保持してはならない。発信者を継続的に同定する台帳を作りたいなら、この線をどちらが持つかの設計が要る
- 失効情報の提供には手数料の定めがある（ガイドライン第4章(3)）。金額は未確認

**スマホ用電子証明書**

- Android 端末は令和5年（2023年）5月11日に搭載開始。iPhone は2025年6月24日に「iPhoneのマイナンバーカード」として提供開始（デジタル庁が2025年6月6日の閣議後会見で公表）
- 搭載できるのは「一定の基準を満たしたチップを搭載したスマートフォン」に限定される。**全機種ではない**
- カード代替電磁的記録は国際標準 ISO/IEC 18013-5 の mdoc data model に準拠した構造
- デジタル庁の資料は、スマホ搭載の今後の利用先として「**災害における利用**」を明示的に挙げている（「今後、順次可能にしていく」欄）。本メモの構想と国の計画は同じ方向を向いており、車輪の再発明にならないよう、着手前に当該施策の現況を確認すること

**失効情報提供の可用性（2026-08-03 一次照合）— 「災害時も継続する」という前提は置けない**

これは本案の生命線として未確認のまま残っていた項目で、同日照合した。結論は、**継続を保証する根拠は見つからず、逆に定常的な非可用時間が公表されている**である。

- 署名検証者向けリポジトリは**毎日 6:00〜7:00 に更新**され、「更新作業時間帯にアクセスした場合、失効記録等を取得できないことがありますので、ご注意ください」と明記されている[高]（<https://www.jpki.go.jp/verifier/verifier.html>）。毎日1時間、取得が保証されない窓がある
- 利用可能時間の案内は「原則として24時間ご利用いただけます。ただし、保守点検等によりサービスを一時的に停止する場合がございます」[高]（<https://www.jpki.go.jp/jpkiguide/support_time.html>）。実際に停止告知が繰り返し出ており、直近の例では令和7年7月25日20:00〜26日8:00 の約12時間停止がある[高]（<https://www.jpki.go.jp/ca/check/schedule/p70.html>）。ただしこれらの告知が名指しするのは利用者クライアントソフト経由の機能で、**民間の署名検証者向け CRL/OCSP 配信がこの停止に含まれるかは記載が無く未確認**
- 公的個人認証法は第18条第1項で機構に提供義務（「…速やかに、保存期間に係る署名用電子証明書失効情報の提供を行うものとする」）を課す一方、**法令本文に「災害」「非常」「天災」「不可抗力」の語を含む条文が存在しない**[高]（e-Gov 法令API の全文で確認 <https://laws.e-gov.go.jp/api/1/lawdata/414AC0000000153>）。非常時の継続義務規定も、非常時を理由とする免責規定も無い——**法は可用性について何も保証していない**
- J-LIS の業務継続計画（BCP）・冗長構成の公表資料は**見つからなかった**。ただし j-lis.go.jp は今回すべて 403 で取得できておらず、「公表されていない」ことの証明にはならない[中]
- 手数料は、CRL 方式が恒久無料化・OCSP 方式が当面無料化とする総務省資料があるが、PDF のテキスト抽出に失敗し検索結果の要約経由の把握にとどまる[中]（<https://www.soumu.go.jp/main_content/000852099.pdf>）

**設計への含意**: 上流が落ちている間に検証を要求すると、本案は「本人確認できないので観測を受け付けない」（災害時に沈黙する）か「検証せずに受け付ける」（誠実性規律を破る）かのどちらかへ倒れる。災害時に効かせるつもりなら、**失効検証が取れないときの振る舞い——縮退時に何を受理し、後追い検証をどう扱うか——を先に決める**必要がある。これは実装以前の設計判断で、L1 の署名方式を決める時点の前提条件になる。

未確認のまま残るもの: 認定審査に要する期間と実費／サービスプロバイダ事業者の一覧と受託条件／民間署名検証者向け配信の稼働条件と SLA（j-lis.go.jp が 403 で読めず未確認）／運用規程（CPS）の可用性条項（PDF のテキスト抽出に失敗）。

### 7-2. 制度以外の制約・リスク [中]

- 本人確認は「なりすまし」を解くが**「観測の正確さ」は解かない**。実名でも人は間違える。正確さは L1 の現場証拠（標識・現地コード・写真）と組み合わせて初めて担保される
- 実名紐付けの萎縮効果と、災害時に発信者の所在が推定されるプライバシー問題
- 「審査員を誰が審査するか」の運用コスト。§2-4（平時に使われない仕組みは本番で使われない）のとおり、平時の役割（例: 平時は地域の設備点検・営業時間更新の報告網）が無いと審査制度ごと形骸化する

**端末依存の非対称設計**（運営者の気づき 2026-08-03: 「個人の名のもとに発信するなら携帯が必須になる」）: そのとおりで、この案は発信者にスマホ（JPKI 読み取りまたはスマホ用電子証明書 + 電池）を要求する。災害時に全員へ端末を仮定すると §2-4 に反して死ぬ。答えは**携帯必須を「審査済み観測者」という少数側だけに閉じ込める**こと——観測者は民生委員・防災士規模の数百人であり、避難所での優先充電や予備電池の事前配備で支えられる。受信側の被災者には端末を一切要求せず、L3 の梯子（紙・標識・ラジオ）で届ける。さらに観測者側にも完全アナログの縮退（帰還者が避難所掲示板へ記入し、運営が転記・署名する）を最下段として残す。

本リポジトリとの関係: save_kumamoto R1 の「読み取り専用・利用者投稿なし」境界は**変えない**。この案は上流（観測・運搬）を担う**別ツール**であり、本アプリはその検証済み出力を読む側に立つ（`ALLOWED_SOURCE_HOSTS` へ検証済みフィードを足すかは、その時点で ADR として判断する）。
