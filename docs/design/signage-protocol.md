# 設計仮説 — 現場状態を宣言する標識プロトコル（L0/L1）

作成: 2026-08-03 / 位置づけ: **設計仮説メモ**（R1 のスコープ外。実装計画ではない）/ 親メモ: [zero-base-rethink.md](./zero-base-rethink.md) の §3 L0「現場状態の標準化」と L1「現場アテステーション」を1枚に起こしたもの。

確度タグ: [高]=公式一次情報で確認済み（出典は §5）/ [中]=複数の根拠から推定 / [低]=仮説・要検証。

> 問い: 給水所・避難所・配布拠点が「いま開いているか」を、現場自身が宣言し、機械で検証できる形にするには何を決めればよいか。

## 1. 一次情報照合の結果 — すでに標準がある範囲 [高]

親メモの初版は「物理標識の標準が国・自治体に無い」と書いていた。照合の結果、**これは不正確**だった。正しくは次のとおり。

### 1-1. 避難誘導の標識には JIS がある

**JIS Z 9098「災害種別避難誘導標識システム」**（平成28年〈2016年〉3月22日制定、2026年3月23日改正）が実在する。2016年版の内容は次のとおり。

- 標識は4種類——**注意標識 / 避難情報標識 / 避難誘導標識 / 避難場所標識**。これらを「状況に応じてシームレスデザインの考え方に基づき途切れることなく提供しなければならない」（洪水・内水氾濫・大規模な火事には注意標識が無い）
- 対象の災害種別は、災害対策基本法の2013年6月一部改正が定めた異常な現象の種類に対応する——津波・洪水・内水氾濫・高潮・土石流・崖崩れ／地滑り・大規模な火事
- 図記号は**新しく作らず、JIS Z 8210（案内用図記号）の既存番号を指定して使う**（避難場所=6.1.4、避難所=6.1.5、災害種別一般=6.5.x、注意=6.3.x、方向矢印=6.4.9）
- **適不適表示マーク**: その避難場所が当該災害に適しているかを「○」「×」で表示する。色は**黒（マンセル値 N1）**を使う、と規格が指定している

**2026年3月23日に改正が公示された** [高]。経済産業省の公示資料（資料5「災害種別避難誘導標識システムに関するJIS改正」）で確認できた改正の要点は次のとおり。

- **JIS Z 9097（津波避難誘導標識システム）を JIS Z 9098 へ統合**した。災害ごとに個別だった規定を共通のシステム構成として一元化している
- 適用する災害種別に **地震・火山噴火を追加**した（改正後: 津波・高潮・洪水・内水氾濫・土石流・崖崩れ／地滑り・大規模な火事・火山噴火・地震）
- 2022年に日本主導で開発された**対応国際規格 ISO 22578 との整合**が改正の背景。用語・定義の見直しと、新たに開発された図記号の追加を行っている
- 火山噴火向けの「噴石シェルタ（退避壕）」など図記号が新設され、適否マークの色分け表示（○=緑・×=赤など）も可能になった [中]

**したがって上の §1-1 の記述（4種類の標識構成・図記号番号・適不適マークの色は黒 N1）は2016年版に基づくものであり、2026年版でどこが変わったかは規格本文を読むまで確定できない。** 用語・定義の見直しと図記号追加が改正内容に含まれる以上、これらの細目は2026年版で変わっている可能性がある（§7-1）。

### 1-2. 避難所の「開設状況を周知する」は業務として定義されている

内閣府「避難所運営ガイドライン」（平成28年4月策定／令和4年4月改定）のチェックリストは、次を市町村の業務として列挙している。

| 項目番号 | 仕事 | 時期 | 主担当 |
|---|---|---|---|
| 2-1 | 避難所の**開設状況**を周知する | 初動・応急 | 防災担当 |
| 2-2 | 避難所の**使用可否**を周知する | 応急 | 防災担当 |
| 2-3 | 避難所の**代替施設開設**を周知する | 応急 | 防災担当 |
| 4-1 | 内部向け情報掲示板を設置する | 応急 | 施設管理者、避難所派遣職員 |
| 5-1 | **外部向け掲示板**を設置する | 応急 | 施設管理者、避難所派遣職員 |
| 5-2 | 在宅避難者への情報発信を実施する | 応急 | 避難所支援班、避難所派遣職員 |

## 2. 差分 — 何が無いか [高]

上の2つを並べると、空白の形がはっきりする。

| | 標準の有無 |
|---|---|
| **静的な属性**（この場所はどの災害に適するか／どちらへ行けばよいか） | **JIS Z 9098 / JIS Z 8210 で標準化済み**。図記号・配色・矢印・○×まで規定がある |
| **動的な状態**（いま開いているか／何時までか／次はいつか／終わったならどこへ） | **標準が無い**。「周知する」「掲示板を設置する」という**業務**は定義されているが、**何をどう書くか**の様式・語彙は定められていない |

加えて2点。

1. **宣言する主体が現場ではない。** 「開設状況を周知する」の主担当は防災担当（市町村本部）で、避難所自身が自分の状態を宣言する形になっていない。親メモ §2-2（最も正確な情報の保持者は現場にいる）の観点では、真実の座が本部側に置かれたままである
2. **避難所以外の拠点が体系の外にある。** JIS Z 9098 が扱うのは避難場所・避難所で、**応急給水所・物資配布拠点・無料入浴施設・仮設トイレ**は対象外。本アプリが実際に扱っているカード（`water-station` / `food-hikawa` / `bath-kumamoto` / `toilet-container`）は、まさにこの体系の外側にある拠点である。**2026年3月改正でもこの空白は埋まっていない**——改正で増えたのは適用する災害種別（地震・火山噴火）と図記号であって、拠点の種類ではない（§1-1）

この2点が、親メモが「上流（観測）が社会側に無い」と言ったことの正確な中身にあたる。無いのは標識そのものではなく、**状態を宣言する語彙と、宣言する主体の設計**である。

## 3. 提案する状態語彙（L0） [低]

現場が掲げる標識に載せる状態を、6語に絞る。語彙を増やさないことが要点で、**読む人が現地で0.5秒で判定でき、書く人が迷わず選べる数**に収める。

| 状態 | 標識の文言 | 意味 | アプリ側の対応物（`lib/disaster-data.ts`） |
|---|---|---|---|
| `open` | **開設中** ◯時まで | いま受け取れる | `serviceWindow` の `open` |
| `before` | **本日 ◯時から** | まだ始まっていない。待てば開く | `serviceWindow` の `before` |
| `between` | **いまは時間外** 次は◯時から | 一度閉まっている。待てば再び開く | `serviceWindow` の `between` |
| `closed_today` | **本日終了** | 今日はもう開かない。明日は未定 | `serviceWindow` の `closed` |
| `moved` | **終了しました** → ◯◯へ | この場所は終わり、行き先がある | **アプリに対応物が無い**（§4 参照） |
| `unknown` | **確認できていません** | 掲げる人が状態を確かめられていない | `sourceStatus: "unavailable"` |

設計の理由:

- **`before` と `between` を分ける。** どちらも「いま閉まっている」だが、前者は待てば開き、後者は一度閉まっている。伝えるべきことが違う（既に `serviceWindow` がこの区別を持っている）
- **`moved` を必ず持つ。** 終了だけを掲げると、そこへ来た人は次にどこへ行けばよいか分からないまま引き返す。親メモ §2-1（最悪の失敗は「行ったら使えなかった」）の対処は、閉じた場所に**次の行き先**を残すことである
- **`unknown` を語彙に入れる。** 状態が分からないときに標識を掲げないと、「標識が無い＝やっていない」と「標識が無い＝誰も更新していない」を区別できない。本アプリが `sourceStatus: "unavailable"` を持っているのと同じ理由
- **「混雑」「満員」を入れない。** 主観が入り、掲げる人によってばらつく。受け入れ可否は現地で聞く

**標識だけが「いま開いている」を断定してよい。** 親メモ §4-1 と `lib/poster.ts` で確認したとおり、紙も画面も「刷った／取得した時刻」でしか判定できないため「いまは受付時間内です」と言い切れない。現場が自分で掲げる標識だけが、掲げた瞬間の事実を断定できる。**この非対称性が L0 を最下段ではなく最上流に置く理由**である。

## 4. アプリ側の型との差分 [高]

上の語彙をそのまま `ActionCard` へ持ち込めるかを確認した結果、**2つ足りない**。

1. **`moved`（移動先）を表現できない。** `ActionCard` は失効（`expiresAt`）を持つが、「終わったので次はここ」を持たない。期限が切れたカードは消えるだけで、次の行き先を残せない
2. **状態の宣言者を持たない。** `sourceName` は出典（＝公式ページ）であって、現場で状態を掲げた人ではない。L1（現場アテステーション）を足すなら、`sourceStatus` とは別に「誰が・どこで・いつ宣言したか」の軸が要る

いずれも R1 では足さない（読み取り専用・利用者投稿なしの境界を変えない）。L2 の設計に入る時点で判断する。

## 5. 既存標準から借りるもの／足すもの [中]

**借りる**（新しく作らない）:

- 図記号は JIS Z 8210 の既存番号を使う。避難所=6.1.5、避難場所=6.1.4、方向矢印=6.4.9。新しい絵を作ると、既に貼られている標識と体系が二重になる
- **適不適マークの設計思想をそのまま借りる。** ○/× を黒（マンセル N1）で出すという規格の指定は、色覚差・モノクロ複写・退色のいずれでも意味が消えないことを狙ったもので、本リポジトリが `docs/design/screens.md` で決めている「欠け方を色ではなく文字で出す」と同じ判断である。状態語彙も**色に意味を持たせず、文字と記号で出す**
- 「シームレスデザイン——途切れることなく提供」という要求も借りる。標識が拠点の入口にしか無いと、手前で引き返せない

**足す**（既存標準に無い）:

- §3 の6語の状態語彙と、その掲示様式
- 日付と時刻の必須表示。静的な標識は「いつの表示か」を持たなくてよいが、状態は持たないと成立しない（`lib/poster.ts` が紙で同じ結論に達している）
- 避難所以外の拠点（給水・配布・入浴・トイレ）への適用

## 6. L1 現場アテステーション — 設計案 [低]

ここから先は未検証の仮説であり、一次情報の照合対象すら定まっていない。

- 標識に印刷した QR に、拠点ID・状態・宣言時刻を載せ、拠点ごとの鍵で署名する。読む側は署名を検証するだけでよく、**運び手を信頼する必要がない**（親メモ §3 L2）
- 鍵の配布・失効・現地での更新手段が未解決。電源も通信も無い場所で状態を更新するなら、日替わりコード表のような紙の運用に落ちる可能性がある
- QR を生成すると本リポジトリに依存が増える。紙レンダラー（`lib/poster.ts`）は依存追加を避けて出典URLを文字列で刷る形にしてあり、L1 に着手する時点で改めて判断する

**着手順序を守ること。** L2（運搬）の技術選定は、L0 の語彙と L1 の署名方式が決まるまで始めない。運ぶものが決まっていないのに運び方は決められない。

## 7. 未確認の残リスク

1. [高] JIS Z 9098 の2026年3月改正は、経済産業省の公示資料で**改正の要点まで一次確認済み**（§1-1）。ただし**規格本文は有償頒布のため未読**であり、図記号番号・寸法・配色といった条文レベルの仕様は未確認。とくに §1-1 に書いた4種類の標識構成・図記号番号・適不適マークの色（黒 N1）は**2016年版の解説資料に基づく記述**で、改正内容に「用語や定義の見直し」「新たに開発された図記号の追加」が含まれる以上、2026年版では変わっている可能性がある。この細目を根拠に実装判断をするなら、先に規格本文の入手（有償）が要る
2. [高] 本メモは JIS の**規格本文を読んでいない**。参照したのは内閣府が公開する解説資料（日本保安用品協会「防災標識ガイドブック」）とガイドラインで、規格の要求事項そのものの引用ではない
3. [中] 避難所運営ガイドラインのチェックリストは確認したが、市町村が実際に使っている掲示様式（各自治体が独自に作っている貼り紙）は調べていない。既に現場で使われている様式があるなら、それを標準化する方が新規設計より速い
4. [低] §3 の語彙は、実際の避難所運営者・給水所担当者に見せて検証していない。使う人が選べない語彙は現場で使われない（親メモ §2-4）
