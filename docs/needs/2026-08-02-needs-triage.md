## 分類基準 — 現行の約束から導いた5テスト

分類は次の3値。(a) 現行アプリ（読み取り専用・カード型・巡回で更新）の延長で作れる / (b) 現行の約束を崩す＝別プロダクト（境界の外と明記して保留） / (c) 作らない（既存サービスがある、またはアプリでは解決にならない）。

| テスト | 内容 | 落ちたら |
|---|---|---|
| 1. 読み取り専用 | 認証・利用者投稿・割当て・個人情報の保持が本質に含まれないか（`docs/design/concept.md`「設計原則」: 収集する経路をコードに持たない） | (b) |
| 2. 稼働判定をしない | 「現在の稼働状況の判定」を引き受けず、公式ページに書かれている記載の転記だけで価値が出るか | 転記で価値が出る範囲まで縮めて (a)、それ以外 (b) |
| 3. 外部通信ゼロ | 事業者・自治体・利用者からの実行時の更新経路が本質に含まれないか（`docs/design/api.md`: 実行時に外部へ出ていく通信は無い） | (b) |
| 4. 運用規模 | 巡回1日1回・人手・19カード7市町村で、唯一の品質基準（鮮度と失効を正直に出す）を維持できるか。維持できない情報は載せない | 維持できる粒度まで縮めて (a)、施設単位の網羅は (b) |
| 5. 既存サービス | 公式の集約・案内が既にあるか | (c) |

## クラスタ（判断単位はこの4つ）

1. **用途別可否をカード内で言い切る**（#1 を筆頭に、#3 #4 #5 #15 の条件付き部分）— 「復旧した／営業中」の二値に対し、用途別の可否（飲める/飲めない、開局/調剤可）と「行く前に確認すること」を既存機構（`verifyPoints` / `facts` / `availableWindows` / `sourceStatus`）で出す。**新しい思想ではなく、現行の約束の適用範囲を広げるもの**
2. **公式情報の横断表示カードの追加**（#10、#7、#6の仮置場情報、#13の受付情報）— 機能開発ではなくカード＝コンテンツの追加。巡回対象が増えるので、追加は運用コストと引き換え
3. **認証済み関係者の内部運用＝別プロダクト**（#2 #11 #12 #14、#6運搬 #13写真 #14割当て）— 現行の約束（読み取り専用・個人情報ゼロ）の外。**このリポジトリでは作らない**と明記して保留。作るなら別プロダクトとして要件からやり直す
4. **既存あり・アプリでは解決にならない**（#8 #9 #16）— 既存の公式集約への導線か、アプリ外の手段が本体。作らない

## R1 候補の推奨（2026-08-02 運営者選定済み: 推奨どおり #1 + #10 の2件）

R1 に入れるのは最大1〜2件（handoff の指定）。絞り込み基準: 既存機構で表現できる / 巡回コスト増分が小さい / 時事性（8/3 に40度予想、断水継続中）/ 運営者記載の優先度。

- **推奨1: #1 水道の中間状態**（クラスタ1の最初の適用先）— 優先度[高]・運営者が共通データモデル化を明記・既存 `verifyPoints` と直結・八代市の試験通水という具体の対象が今ある。「用途別可否＋最終確認時刻」をカード単位で持つか項目単位で持つかが ADR の論点
- **推奨2: #10 寄付窓口の判別**（クラスタ2の最初の1枚）— 全テストを確度[高]で通る唯一の新カード。鮮度リスクが最も低く、巡回コスト増分が最小。不可逆な操作（送金）の前に確認を挟む点で既存の提供価値と同型

次点: #15（薬局の注記）は推奨1のデータモデルが決まれば同型で入れられるため、R1 では#1に含めず様子を見る。#3（猛暑）は時事性最高だが、アプリが言い切れることが公式記載の転記に限られ、原文の照合なしに範囲を確定できない。

### #17 停電情報 — 九州電力送配電の公式停電情報ページ（2026-08-02 観測）

- 観測: 運営者より「九州電力送配電が停電（配電）の情報ツールを出している」（https://www.kyuden.co.jp/td_teiden/kyushu.html）
- 一次確認[高]（2026-08-02 WebFetch 実測）: 提供主体は九州電力送配電。おおよそ5分以上の停電を対象に集計。当該ページは九州全域の粗い粒度で、地域単位の停電情報ページが別にあると案内。更新頻度・最終更新時刻はページ上に記載なし。熊本県への個別言及なし
- 分類: **(a)条件** [高] — 公式ページへの導線と「何を確認すべきか」の注記まで。**停電件数・復旧見込みの数値は転記しない**。分単位で変わる情報を巡回1日1回で写すのは、唯一の品質基準（鮮度と失効を正直に出す）と正面から衝突する。公式に生きたツールがある領域では、アプリの役割は複製ではなく導線
- 制約: kyuden.co.jp は `ALLOWED_SOURCE_HOSTS`（機械強制・現行7ドメイン）に未登録。カード化するならドメイン追加とテスト更新が要る（小さいが明示的な変更）
- R1への影響: **R1選定（#1 + #10）は変えない**。#1 の ADR-0003 で「ライフライン別の扱いの違い（電力=公式ツールへのリンク型、水道=公式発表の転記型）」の文脈として参照する

### #18 特務機関NERV防災アプリとの棲み分け・導線（2026-08-03 運営者提案）

- 観測: 運営者より「こちらのアプリの方が進んでいて情報が提供されている部分があると思うので、連携するというか、NERV のダウンロード・インストールを推奨して、NERV で見れる部分は NERV でカバーしてもらうイメージ」（https://nerv.app/about.html。`handoff-2026-08-03-poster-signage-jpki-done.md` Acceptance 3 から転記）
- 一次確認[高]（2026-08-03 WebFetch 実測、nerv.app/about.html）: 提供主体はゲヒルン株式会社（防災科研・TBSテレビ・NEWS DIG 合同会社と連携）。提供情報は緊急地震速報・地震・津波・火山・気象警報・雨雲レーダー・キキクル・河川水位・台風・Jアラート等の**広域警報系**が本体。加えて「クライシスマッピング」レイヤーで避難所・給水所の位置・トイレ設備・災害ごみ収集場所・入浴支援・救援物資の配布地点を扱う
- **前提仮説の訂正**: handoff の「生活支援拠点が NERV の守備範囲に含まれないなら棲み分けは自然に成立」は**名目上は不成立**（守備範囲は重なる）。ただしクライシスマッピングは**サポーター会員のユーザー投稿方式**（現在地10km圏内を投稿、ゲヒルンがレビュー+サポーター同士で修正・削除）で、about ページ自身が「現在はほとんどの情報が未記入の状態」と記載する[高]。本アプリの「公的機関の公式ページに書かれている記載だけを転記し、鮮度と失効を機械で出す」とは**信頼モデルが別物**であり、実質の棲み分けは「警報系=NERV / 公式発表の転記と失効管理=本アプリ」で成立しうる[中]
- 利用規約[高]（2026-08-03 WebFetch 実測、gehirn.co.jp/policies/nervappterms/、2024-09-01 改定）: 外部からのリンク・ダウンロード推奨の紹介・名称やロゴの利用・情報の再配信について、可否の明示条項は**いずれも無し**。導線を置くなら名称・ロゴの扱いは相手方（ゲヒルン社）への確認が要る可能性がある（くまモン届出と同種の確認）
- 分類: **(a)条件** [中] — 導線と「何を確認すべきか」の注記までなら5テストのうち1〜4は通る。テスト5の線は #17 と同じ「公式に生きたツールがある領域では、アプリの役割は複製ではなく導線」で、特に**広域警報系は本アプリが最初から引き受けていない領域**（concept.md「引き受ける範囲」参照）なので、そこを NERV へ送るのは目的関数（無駄往復の最小化）に整合する。ただし #17（公的性格の強いインフラ事業者の公式ページ）と違い、こちらは**民間アプリのインストール推奨**であり、`ALLOWED_SOURCE_HOSTS` の「運営主体が公的機関だと確認できたものだけを個別列挙」という方針の変更にあたるため **ADR 案件**
- やってはいけないこと: NERV の提供情報（警報・クライシスマッピングとも）を本アプリへ転載・再配信すること。誠実性規律（出典に書かれている記載だけを出す・巡回で照合する）を他アプリの画面越しには維持できない
- 運営者判断が必要な点: (a) 導線を置くか（置くなら ADR 起案が前提） (b) 置く位置（カードとして持つか、concept.md「引き受けない範囲」の but-see として書くか） (c) 名称・リンク利用の相手方確認をどこまでやるか
- R1への影響: **R1選定（#1 + #10）は変えない**
