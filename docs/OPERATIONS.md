# 運用手順（訂正・停止）

作成日：2026年7月31日

誤った案内を出してしまったときに、**誰が・どうやって・どこまで**止められるかを定義する。
`README.md` の No-Go #2「運営・訂正体制」と、`docs/RELEASE_AUDIT.md` の公開停止条件 #2・#3 に対応する。

**対象は Web のみ。** iOS / Android のネイティブアプリには停止経路が一切ない（第3章の到達範囲表を参照）。

## 凡例

| 記号 | 意味 |
|---|---|
| `[要記入]` | **実在の値がまだ決まっていない。** 埋めるまで公開しない。推測で埋めてはいけない |
| `[提案]` | この文書からの提案。運営者が承認するまで確定ではない |
| `[高]` `[中]` `[低]` | 確度。`[高]`=このリポジトリのコード・コマンド出力・公式資料で直接確認済み |

## 1. 位置づけ

このアプリは公式サービスではなく、有志が公式情報への導線をまとめたもの。したがって
**間違いは「起きうる」前提**で運用する。守るべき順序は次のとおり。

1. 命に関わる誤り（誤った避難先、存在しない給水地点、間違った電話番号）を**止める**
2. 止めたことを利用者に**わかる形で**示す（黙って消さない）
3. 正しい情報へ**訂正**する
4. 訂正できないなら「現在の状況は確認できません」と**正直に出す**

「見えなくする」ことと「直す」ことは別。止めるのは即時、直すのは確認が取れてから。

## 2. 役割と連絡体制

現在は**運営者1人がすべてを兼務する**。将来分割できるよう役割は分けて書くが、
今の担当者列はすべて同じ人物を指す。

| 役割 | やること | 現在の担当 |
|---|---|---|
| 停止判断者 | 縮退モードを立てる／解除するかを決める | `[要記入]`（運営者本人） |
| 訂正担当者 | `lib/disaster-data.ts` を直し、再生成・検証・デプロイする | 同上 |
| 問い合わせ対応 | 外部からの誤り報告を受け、重大度を判定する | 同上 |

`[要記入]` に入れる表示名について: 問い合わせ窓口を GitHub Issues にする以上、
**GitHub アカウント名が事実上の公開名**になる（コミット履歴にも表示される）。
本名を出すかどうかは運営者が決める。

### 単一障害点であること［高］

1人兼務なので、その人が対応できない間は**誰も止められない**。これは受け入れる前提であって、
解決済みの問題ではない。部分的なフェイルセーフは1つだけある。

- 13カードは `expiresAt`（`lib/disaster-data.ts` の `contentTimes`）を共有し、**24時間で一斉に失効**する
  （2026-07-31 ユーザー確定、第5章参照）。medical カード1件のみ個別の `staleMedicalTimes` を使う。
  失効すると各カードは「現在の状況は確認できません」へ切り替わり、行動手順と公式リンクだけが残る
- ただしこれは**最大24時間かかる**。今まさに危険な誤案内には無力。停止スイッチの代わりにはならない

### 問い合わせ窓口

| 項目 | 値 |
|---|---|
| 経路 | **GitHub Issues（このリポジトリ）** |
| URL | `[要記入]` — **remote が未設定なので現時点では存在しない**［高］。公開の前提条件 |
| 対応可能時間 | **9:00〜21:00 JST**、ベストエフォート（応答時間は約束しない） |

正直に書いておくべきこと:

- GitHub Issues は**被災者本人にはほぼ使えない**。GitHub アカウントが要るうえ、
  停電・低速回線の下で開く導線ではない。実質的には支援者・自治体職員・開発者向けの経路
- 夜間（21:00〜翌9:00）に届いた誤り報告は**翌朝まで残る**。この時間帯に危険な誤りが出た場合、
  頼れるのは `expiresAt` の失効（確認から24時間）だけになる。24時間期限では夜間中に
  失効しないこともあるため、夜間の危険な誤りは自動では守れない
- `[提案]` 被災者からの導線が必要になったら、`/status` にメールアドレスか
  フォームURLを出す（第7章）。実値は `[要記入]`

## 3. 停止のランブック

### 3.1 重大度の分類

| 区分 | 例 | 対応 | 所要 |
|---|---|---|---|
| **A：即時縮退** | 誤った避難先、存在しない給水地点、間違った緊急連絡先、公式が否定した情報 | 縮退モードを立てる（全カードを止める） | 数分 |
| **B：当該カードのみ訂正** | 1件の受付時間・場所・URL の誤り。他カードは正しい | 縮退せず訂正だけデプロイ | 数十分 |
| **C：次回定時** | 表現の分かりにくさ、優先順位、誤字 | 通常の更新に含める | 次回 |

**迷ったら A**。カードを止めても 119・110 と自治体公式への導線は残るので、
止めることによる損失は「案内が見えなくなる」だけ。誤案内を出し続ける損失の方が大きい。

### 3.2 止める（区分A）

**再ビルド・再デプロイは不要。環境変数を1つ設定するだけ**［高］。

```bash
npx wrangler secret put EMERGENCY_MODE
# 値の入力を求められたら true と入れる
```

1. 上のコマンドを実行する
2. `/status` を開き、**「緊急縮退中」**と表示されることを確認する
3. `/` を**別の端末または別ブラウザ**で開き、個別カードが消えていることを確認する
   （自分の端末だけだとキャッシュを見ている可能性がある）
4. 止めた事実・時刻・理由を記録する

**なぜ Secret なのか**［高］: `wrangler deploy` は既定で **vars を全消ししてから設定ファイルの
vars を入れ直す**。`dist/server/wrangler.json` の `vars` は `{}` なので、ダッシュボードで
plain text var として設定した `EMERGENCY_MODE` は**次のデプロイで消える**。
停止中に誰かが文言修正をデプロイした瞬間に案内が復活する、という事故が起きる。
secrets はデプロイで消えず、かつ `process.env` に載る。
どうしても plain var で運用するなら、**すべてのデプロイで `--keep-vars` を付ける**。

### 3.3 解除する

```bash
npx wrangler secret delete EMERGENCY_MODE
```

`/status` が「通常表示」に戻ることを確認する。secret は読み出せないため、
**`/status` が現在の停止状態を知る唯一の経路**になる。

### 3.4 停止が届く範囲［高］

止めても全員に届くわけではない。これを理解せずに「止めた」と言わない。

| 対象 | 届くか | 遅延 |
|---|---|---|
| オンライン利用者の次のページ遷移・再読込 | **届く** | 次のナビゲーションまで（`public/sw.js` は navigation を network-first で取りに行く） |
| 開きっぱなしのタブ | **届かない** | 利用者が再読込するまで（ポーリング未実装） |
| オフラインの PWA 利用者 | **届かない** | 再接続してナビゲーションするまで（`sw.js` がキャッシュ済みの `/` を返す） |
| iOS / Android ネイティブ | **一切届かない** | ストア審査を通した新バージョンの配布まで（数日〜） |

ネイティブに届かない理由［高］: `expo-updates` を入れておらず、`app.json` に `updates` /
`runtimeVersion` の設定もない。カードデータはアプリに同梱されており、起動時に何も取りに行かない
（通信ゼロ設計）。これは privacy 上の判断の裏返しであって、バグではない。
**この非対称を運営者が受諾するまで、ストア申請はしない。**

### 3.5 停止スイッチ ≠ 失効表示

混同しやすいので分けて書く。

- **停止スイッチ**（`EMERGENCY_MODE`）: 運営者が意図して止める。サーバー側で判定するので
  ネイティブとオフライン利用者には届かない
- **失効表示**（`isExpired`）: `expiresAt` を過ぎたカードを自動的に「現在の状況は確認できません」へ
  切り替える。**端末の時計で動く**ので、オフラインでもネイティブでも効く

つまり失効表示は、停止が届かない利用者に対する**唯一の自動的な劣化通知**。
だから `expiresAt` を安易に延ばしてはいけない。

### 3.6 変えてはいけないもの［高］

停止スイッチが黙って効かなくなる変更。

- `nodejs_compat` を外す / `compatibility_date` を `2025-04-01` より前へ下げる
  → Workers が bindings を `process.env` へ流し込まなくなる（`vite.config.ts` で固定済み）
- 環境変数名に `NEXT_PUBLIC_` を付ける
  → vinext がビルド時に rsc/ssr を含む全環境へ define するため、値がサーバー側へ焼き付き、
  以後どの環境変数を変えても止まらなくなる
- `vinext build --prerender-all` を使う → `/` が静的化されると環境変数が効かない
- クライアントコンポーネントから停止フラグを読む → クライアントバンドルでは
  `process.env` が `{}` に置換され常に false になる（**これが 2026-07-31 に直した不具合そのもの**）

上の4つは `npm test` の `tests/emergency-mode.test.mjs` が機械的に検出する。
テストを消したり緩めたりしないこと。

## 4. 訂正のランブック（区分B）

```bash
# 1. 正典を直す（Web とネイティブの唯一の情報源）
#    lib/disaster-data.ts

# 2. ネイティブ用データを再生成する（忘れると Web とネイティブで内容がずれる）
npm run gen:mobile-data

# 3. 検証
npm run lint && npm test

# 4. デプロイ（Human Approval Gate。承認を得てから）
```

`npm test` には「正典を編集して再生成し忘れていない」という検査が入っている。
`git status` に `apps/mobile/src/data/actions.ts` の差分が残っていたら、手順2を飛ばしている。

### 直せる範囲の非対称［高］

| | Web | ネイティブ |
|---|---|---|
| 誤りを訂正する | デプロイで即時 | **ストア審査を通すまで不可（数日〜）** |
| 案内を止める | 環境変数で数分 | **不可** |

したがって**ネイティブに載せる情報は、Webよりも保守的にする**。
「24時間で変わる可能性がある値」をネイティブへ同梱するのは、そもそも設計が合っていない。

## 5. 情報の鮮度運用

### 巡回の判定ルール［高］

**リンクが生きていることと、そのページにカードの話題があることは別**。
リンク生存と「内容が変わっていない」ことだけを見る確認では、リンクが生きたまま
中身だけ話題を失う壊れ方を検出できない。判定はこの順で行う。

```text
1. リンクを開く
2. カードの steps に書いた行動が、そのページで実行できるか
   → できる  : sourceStatus は official のまま。checkedAt を更新する
   → できない: 同じ話題の実在ページを探す
       → 見つかった  : 導線を再選定し、カード文言を実態に合わせる
       → 見つからない: sourceStatus を "unavailable" にし、
                       unverified に「何が確認できていないか」を書く
```

`unavailable` にしたカードも `checkedAt` は更新してよい。
「確認できないことを、その時刻に確認した」という事実は正しいため。

### 巡回時に書き換える場所［高］

`lib/disaster-data.ts` の冒頭にある**2つの定数だけ**を書き換える。

```ts
const PATROL_AT = "2026-07-31T20:16:00+09:00";
const PATROL_EXPIRES_AT = "2026-08-01T20:16:00+09:00";  // PATROL_AT + 24時間
```

各カードは `...patrolled(publishedAt)` または `...patrolled(publishedAt, "unavailable")` で
この2つを共有する。`publishedAt` は出典ページに表示されている最終更新日で、
日付しか出ていないページは 00:00 へ切り下げる（鮮度を実際より新しく見せないための保守側の値）。

書き換えたら次を実行する。

```bash
npm run gen:mobile-data && npm test
```

- `expiresAt` は `checkedAt` の**24時間後**（旧: 4時間後。2026-07-31 ユーザー確定、下記「採用」を参照）

### 論点（採用済み／`[提案]`）

4時間という設定は「災害時の情報は4時間で古くなる」という判断としては妥当だが、
**巡回できる頻度と釣り合っていない**。1人運用で4時間ごとに14件を再確認するのは持続しない。
選べる方向として3つを検討した。

1. **カテゴリ単位で期限を分ける** — 「熊本県の公式ページを開く」のような導線カードは
   1日単位でも実質劣化しない。一方「今日の給水地点」は4時間でも長い。
   現在は全件が同じ値を共有しているので、劣化速度の違いを表現できていない
2. **`checkedAt` だけを更新する軽い確認ルーチン** — 「リンク先が生きていて、
   掲載内容が変わっていない」ことだけを確認して時刻を延ばす。中身の再確認より軽い。
   ただし**リンクが生きていることと内容が正しいことは別**なので、
   これで延ばしてよいのは導線カードだけ
3. **巡回頻度に期限を合わせる** — 1日1回しか見られないなら `expiresAt` も1日にする。
   ただし**期限を延ばすこと自体は情報を新しくしない**。「4時間で失効するが誰も更新していない」
   状態と「24時間有効ということにしている」状態では、後者の方が危険

**採用（2026-07-31 ユーザー確定）**: 提案1＋2を採用し、期限を**24時間**とした。
本アプリの全カードは公式サイトへの導線カードであり、1人運用の1日1回巡回の現実的な頻度と
釣り合わせるための判断。提案3（巡回頻度に期限を合わせるだけ）単独は採用していない。
期限を延ばすこと自体は情報を新しくしないため、
**24時間ごとの再確認巡回を止めた場合は、この判断の前提が崩れる**。

**提案2の「軽い確認」の中身を、同日 18:30 の巡回結果を受けて修正した**。
当初は「リンク先が生きていて、掲載内容が変わっていない」ことだけを見る想定だったが、
これでは**リンクが生きたまま中身だけ話題を失う壊れ方を検出できない**ことが実地で判明した
（14カード中6カードが該当）。確認の単位は「リンクが生きているか」ではなく
「**カードの steps に書いた行動がリンク先で実行できるか**」とする（上記「巡回の判定ルール」）。
リンク生存だけで `checkedAt` を延ばすことは、実質的に鮮度の捏造にあたるため行わない。

**同日 20:16 の巡回で、この修正でもまだ緩かったことが分かった**。18:30 の確認は
「そのページにカードの話題があるか」で止まっており、「カードの手順が約束していることが
できるか」までは見ていなかった。手順1つずつを突き合わせたところ、掲載継続としていた8件のうち
4件（medical / shelter / communication / roads）で手順が実行できなかった。
**確認は手順単位で行う**。カードの話題がページにあることは、手順が実行できることを意味しない。

**やってはいけないこと**: 公式ページを再確認せずに `expiresAt` だけ延ばす。
これは鮮度の捏造であり、このアプリが唯一守ると約束した品質基準に反する。

## 7. UIへの反映（`[提案]`）

現在 `/status` には停止状態と安全上の境界しか出ていない。問い合わせ先は出していない。

- `[提案]` `/status` に「誤りを見つけたら」の1行と窓口を出す。実値は `[要記入]`
- 個人情報を晒さない設計にする。個人のメールアドレスを公開ページに直書きすると、
  永続的に収集ボットの対象になる。GitHub Issues か、専用アドレスか、フォームを使う
- **トップページ（`/`）には出さない**。被災者が最初に見る画面は「いま何をするか」であって、
  運営者への連絡ではない。119・110 の導線と competing させない
